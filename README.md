# 🏠 Кампус-отели Диск и Облако — поиск соседей по комнате

Сервис для поиска соседей в комнату кампус-отеля (на 2–4 человека). Показывает анкеты
студентов с фото и краткой информацией, а связаться можно прямо в Telegram.

## Стек

- **Бэкенд:** Python, FastAPI, SQLAlchemy
- **База данных:** PostgreSQL
- **Фронтенд:** React, Vite (в проде — сборка отдаётся через nginx)
- **Инфраструктура:** Docker, Docker Compose

## Возможности

- **Выбор пола на входе:** парни живут с парнями, девушки — с девушками, поэтому
  первым экраном спрашивается пол, и лента показывает только «своих». Выбор
  сохраняется в `localStorage` и меняется кнопкой «Сменить» в шапке
- **Фото:** загружается файлом (не ссылкой). Бэкенд проверяет, что это картинка,
  ужимает до 800px по большей стороне и сохраняет как JPEG
- **Аватар из Telegram:** можно подставить фото и ник из профиля Telegram —
  через Login Widget (обычный веб) или Mini App SDK (сайт открыт внутри Telegram).
  Требует токен бота, см. раздел ниже
- **Три раздела:** «Ищут соседей» (кто ещё сам по себе), «Комнаты» (кто уже
  договорился) и «Блок». Комната — просто группа людей, без номеров и секций:
  видно состав, сколько мест занято (`2/3`) и сколько свободно. Двое сошлись —
  собирают комнату на 3 и ищут третьего; человек из комнаты пропадает из
  раздела одиночек
- **Блоки:** в «Диске» комнаты объединяются попарно в блок на 6 человек — 2+4
  или 3+3. Объединяются целыми комнатами: одна зовёт, и согласиться должны
  **все** жильцы позванной. Комната в блоке не меняет размер (иначе в блоке
  перестанет быть 6), а выход одной комнаты распускает блок целиком. В «Облаке»
  блоков нет, и вкладка там не показывается
- **Вступление только по согласию:** никто не заходит в комнату сам. Летит
  заявка, и её должны подтвердить **все**, кто уже внутри. Любой отказ —
  заявка отклонена
- **Бот в Telegram** пишет про новые заявки (с кнопками «Принять / Отклонить»),
  про решение по твоей заявке и про выход соседа из комнаты
- Лента анкет карточками: фото, имя, направление, о себе. Направление — одно из
  пяти: Разработка, Бизнес, Дизайн, ИИ, Не определился. Возраст и курс не
  собираются и не показываются (колонки `age`/`course` оставлены в БД
  nullable — если понадобятся, вернуть легко)
- Метки: режим сна (сова/жаворонок), курение, чистоплотность, желаемый размер
  комнаты. Размеров можно указать несколько — «хочу 3 или 4, но не двухместную»;
  ничего не выбрано — подойдёт любая
- Фильтры: размер комнаты, режим сна, курение + поиск по тексту
- Кнопка «Написать в Telegram» ведёт на `t.me/username`
- Форма «Разместить анкету» — добавление своего профиля (пол подставляется автоматически)
- **Темы:** светлая и тёмная, по умолчанию — системная. Переключатель в шапке
  циклом: Системная → Светлая → Тёмная. Выбор хранится в `localStorage`, в режиме
  «Системная» приложение следит за сменой темы ОС на лету

## Запуск через Docker (рекомендуется)

Всё поднимается одной командой — Postgres, бэкенд и фронтенд:

```bash
docker compose -p obshaga up -d --build
```

> Флаг `-p obshaga` задаёт имя проекта, потому что имя папки кириллическое
> и Docker его не принимает как имя проекта по умолчанию.

После старта:

- Приложение — http://localhost:5173
- API и Swagger — http://localhost:8000/docs
- Postgres — на хосте проброшен на порт **5433** (внутри сети — `db:5432`)

При первом старте бэкенд дожидается готовности БД и создаёт таблицы. Демо-анкет
нет — сервис стартует пустым, первые анкеты появляются, когда их разместят люди.
Данные хранятся в volume `pgdata` и переживают перезапуск контейнеров.

Полезные команды:

```bash
docker compose -p obshaga logs -f backend   # логи бэкенда
docker compose -p obshaga down              # остановить (данные сохранятся)
docker compose -p obshaga down -v           # остановить и стереть данные БД
```

## Telegram: бот и аватарки

### Куда класть токен

Скопируй пример и заполни — `docker compose` подхватит `.env` сам,
файл уже в `.gitignore`:

```bash
cp .env.example .env
```

```ini
TELEGRAM_BOT_TOKEN=123456789:AA...      # от @BotFather
TELEGRAM_BOT_USERNAME=my_campus_bot     # ник бота без @
BOT_SECRET=<длинная случайная строка>   # openssl rand -hex 32
SITE_URL=https://твой-домен            # для ссылок в сообщениях бота
```

Запуск вместе с ботом (бот под профилем, чтобы без токена не мешал):

```bash
docker compose -p obshaga --profile bot up -d --build
docker compose -p obshaga logs -f bot
```

`BOT_SECRET` — общий секрет бота и бэкенда. Бот действует от имени
Telegram-пользователя, поэтому служебные ручки `/api/bot/*` закрыты этим
заголовком: без него голосовать за других смог бы кто угодно.

### Как включить уведомления (со стороны студента)

1. разместить анкету на сайте, указав свой ник;
2. написать боту `/start` — он найдёт анкету по нику (или по подтверждённому
   Telegram-аккаунту) и запомнит чат.

Шаг 2 обязателен: **бот не может написать первым тому, кто не начал с ним
диалог** — это ограничение Telegram, а не проекта. Пока человек не нажал
`/start`, уведомления ему просто не уходят, сайт при этом работает как обычно.

Команды бота: `/start` — включить уведомления, `/pending` — заявки, ждущие
твоего решения.

### Аватарки из профиля

Без этих настроек кнопка входа через Telegram просто не показывается, а загрузка
фото файлом работает как обычно.

Важно понимать ограничение: **получить аватар по @username нельзя.** Bot API
отдаёт фото только тем, кто уже писал боту, и ищет по `user_id`, а не по нику.
Поэтому аватар берётся только после того, как человек сам подтвердит вход.

### 1. Завести бота

В [@BotFather](https://t.me/BotFather): `/newbot` → получаешь токен вида
`123456789:AA...`. Затем `/setdomain` → указываешь домен сайта.

### 2. Передать токен

```bash
export TELEGRAM_BOT_TOKEN="123456789:AA..."
export TELEGRAM_BOT_USERNAME="my_campus_bot"
docker compose -p obshaga up -d
```

### 3. Что заработает

- **Обычный браузер** — показывает понятный переход в Telegram Mini App. Подписанные данные старого Login Widget по-прежнему проверяются API, но не заменяют вход в мини-приложение для действий с анкетой.
- **Mini App** — если открыть сайт внутри Telegram (кнопка у бота через
  `/setmenubutton` или inline-кнопка `web_app`), приложение само предложит
  «Взять фото и ник из Telegram». Нужен публичный HTTPS-адрес.

### Как это защищено

Telegram подписывает данные HMAC-SHA256 на основе токена бота, и сервер
проверяет подпись сам — схемы у Login Widget и Mini App разные и не
взаимозаменяемы. Подпись старше суток, время более чем на минуту в будущем, неоднозначные параметры и некорректный Telegram ID отклоняются.

Галочку «подтверждён» ставит **только сервер** после повторной проверки подписи
при создании анкеты: клиент не может объявить себя подтверждённым, а ник берётся
из подтверждённых данных, чтобы нельзя было указать чужой.

Аватар скачивается и сохраняется у нас — ссылки `t.me/i/userpic/...` живут недолго.

## Запуск без Docker (для разработки)

Нужен запущенный PostgreSQL. Строка подключения задаётся переменной
`DATABASE_URL` (по умолчанию `postgresql+psycopg2://obshaga:obshaga@localhost:5432/obshaga`).

### 1. Бэкенд (порт 8000)

```bash
cd backend
python3 -m venv venv
source venv/bin/activate                    # Windows: venv\Scripts\activate
pip install -r requirements.txt
export DATABASE_URL=postgresql+psycopg2://obshaga:obshaga@localhost:5432/obshaga
uvicorn main:app --reload --port 8000
```

### 2. Фронтенд (порт 5173)

```bash
cd frontend
npm install
npm run dev
```

Открыть http://localhost:5173 . В dev-режиме запросы к `/api` проксируются
на бэкенд (настроено в `vite.config.js`).

Фильтры для `GET /api/profiles`: `gender`, `track`, `room_capacity`, `smoking`,
`sleep_schedule`, `search`, `without_group` (`true` — только те, кто ещё не в
комнате). `room_capacity` — одно число: подходят те, кто выбрал этот размер

`track` — одно из `dev` | `business` | `design` | `ai` | `undecided`; русские
подписи живут на фронтенде (`src/labels.js`). `search` ищет по имени и «о себе»:
направление теперь выбирают фильтром, а не текстом.

### Правила комнат и заявок

Проверяются на сервере:

- вступить напрямую нельзя — только заявка;
- заявку должны подтвердить **все**, кто сейчас в комнате; любой отказ — отклонение;
- голосовать могут только жильцы этой комнаты (`403`), сам заявитель — не может;
- в комнату пускают только свой пол (`403`);
- нельзя состоять в двух комнатах сразу (`409`), нельзя подать вторую заявку в
  ту же комнату (`409`);
- места перепроверяются в момент одобрения: пока голосовали, их могли занять;
- голос вышедшего перестаёт учитываться — иначе заявка висела бы вечно;
- когда выходит последний жилец, комната удаляется.

### Правила блоков

- блоки есть только в «Диске» (`campuses.WITH_BLOCKS`), размер блока — 6 человек;
- пара подбирается по размеру комнат: 2+4 или 3+3, третью комнату не добавить;
- предложение должны принять **все** жильцы позванной комнаты; любой отказ —
  отклонение (то же правило, что у заявок в комнату);
- пол и кампус-отель у комнат должны совпадать;
- комната в блоке не меняет размер (`409`) — иначе в блоке перестанет быть 6;
- пара перепроверяется в момент одобрения: пока голосовали, размер комнаты
  могли изменить или она успела собрать блок с другими;
- выход одной комнаты распускает блок целиком — половина блока смысла не имеет;
- когда комната распадается, её блок распускается вместе с ней.

В рабочем режиме личность определяет сервер по свежей подписи Telegram. ID в `localStorage` — только подсказка интерфейсу и не даёт прав на анкету. Владельцем считается аккаунт с тем же неизменяемым Telegram ID, а не с похожим ником. Старые непривязанные анкеты не удаляются; восстановление их привязки требует проверки администратором, автоматического захвата по нику нет. При отсутствии токена API отвечает `503`, а админка остаётся закрытой.

## Обновление «Рядом · Соседи»

Общая спокойная палитра и собственные SVG-знаки, компактные настройки ленты, понятный вход по кампус-отелю и сворачиваемые фильтры. Телефон и Telegram WebView используют те же маршруты и прежние ключи прогресса/анкеты. Telegram SDK загружается с собственного сервера.

Ленты анкет, комнат и блоков загружаются независимо; поиск обновляет только анкеты. Предыдущий запрос отменяется, а поздний ответ не заменяет более свежую подборку. На экране сначала до 24 карточек, остальные доступны по «Показать ещё». Загрузка и ошибки имеют отдельное состояние и повтор по нажатию; временная ошибка не удаляет сохранённый ID своей анкеты. Полные данные анкет не кэшируются в localStorage.

Состав комнат загружается двумя SQL-запросами для всей выборки; блоки с комнатами и жильцами — тремя. Тесты проверяют это на синтетических 90 комнатах, без обращения к рабочей базе. Ограничения кампус-отеля, пола и Telegram-авторизация сохраняются. Бот сразу подтверждает нажатие кнопки и затем сообщает результат; соединение с API переиспользуется, автоматического повтора голосований нет. Команды /search и /help открывают поиск.

Проверки в изолированном Python-окружении с зависимостями backend и bot:

```sh
python -m unittest discover -s tests -v
npm ci --prefix frontend
npm test --prefix frontend
npm run build --prefix frontend
```

Forgejo проверяет PR до сборки образов. Интерфейс проверяется на Node 24, а Python-тесты изолированы в `scripts/ci.Dockerfile` с тем же Python 3.13, что и приложение, поэтому не требуют Python из кэша ОС runner. Main автоматически обновляет dev; публикация prod сохраняет существующий workflow_dispatch с deploy_prod=true. Проверка версии: `/api/health` и `/version.json` содержат SHA образа, собранного CI.


### Явные GitOps deploy-jobs в Forgejo

`deploy-dev` и `deploy-prod` в `.forgejo/workflows/ci-cd.yml` — обычные runner jobs со своими checkout и шагом публикации. Это исключает вложенный `workflow_call`, который Forgejo пропускал внутри успешно завершившегося wrapper-job. Старый `.forgejo/workflows/deploy.yml` оставлен для истории и больше не вызывается из CI/CD. Успех сборки или wrapper-job сам по себе не означает публикацию: в запуске должны успешно завершиться реальные шаги `Publish dev/prod image references to GitOps`.

Dev зависит от сборки всех трёх образов; prod — от dev и запускается только вручную с `deploy_prod=true`. У окружений остаются отдельные concurrency-группы. Исходники checkout находятся в `source` с отключённым сохранением credentials. Homelab checkout находится в `homelab`, использует GitHub и прежний `HOMELAB_DEPLOY_KEY`; новых ключей и секретов нет. Node 24 устанавливается тем же действием, что уже используется в check-job.

`scripts/deploy-images.mjs` принимает только `dev`/`prod` и полный SHA из 40 строчных hex-символов. До записи проверяет чистоту GitOps checkout и все три отслеживаемых обычных `values.yaml`; меняет только `repository` и `tag` верхнеуровневого `image`. Комментарии, кавычки, окончания строк, другие поля и приложения сохраняются; неподдерживаемая структура приводит к ошибке до записи. В commit попадают только три ожидаемых файла. После отказа push допускается до двух `pull --rebase` и ещё двух попыток push; конфликт или окончательный отказ остаются ошибкой CI, force-push не используется. Уже актуальные значения не создают повторный commit.

Проверка только на синтетическом временном bare-репозитории, без доступа к настоящему homelab:

```sh
node --check scripts/deploy-images.mjs
node --test scripts/deploy-images.test.mjs
```

Предварительный просмотр для отдельной локальной копии (без записи, staging, commit и push):

```sh
node scripts/deploy-images.mjs --repo /path/to/local-fixture --environment dev --tag <40-hex-SHA> --dry-run
```

После реальной публикации Argo CD применяет обновлённые ссылки на образы. `/api/health` и `/version.json` должны подтвердить тот же SHA; этот фикс не меняет рабочую БД, DNS или конфигурацию Argo CD.

Все runner jobs используют один зафиксированный образ с Docker/Node/Git. Проверки и сборка образов выполняются на существующем runner организации с меткой `homelab-docker`: общая метка `ubuntu-latest` также назначена worker без Docker daemon. GitOps jobs не требуют Docker и сохраняют метку `ubuntu-latest`. Сокет, разрешения и Docker daemon не меняются, новый daemon workflow не запускает.


## Безопасность и локальная проверка

Локальные синтетические стенды без токена включаются только двумя явными параметрами: `APP_ENV=development` и `ALLOW_INSECURE_DEV_AUTH=1`. На рабочем сервере их не задают. Этот режим не открывает админку. Для проверки настоящей границы доступа предпочтительнее тестовый токен и подписанные синтетические пользователи, как в `tests/test_security.py`. Настоящие Telegram-аккаунты, рабочую базу и действующие секреты тесты не используют.

Проверки: `.venv/bin/python -m unittest discover -s tests`, затем в `frontend/` — `npm test && npm run build`. Для бота зависимости устанавливаются отдельно из `bot/requirements.txt`. Подробности контролей и границ проверки — в [SECURITY.md](SECURITY.md). CI и развёртывание при этом не меняются.

`docker-compose.yml` — локальный стенд: порты БД, API и frontend привязаны к `127.0.0.1`, поэтому не открываются всей сети. Примерные пароли в нём предназначены только для разработки. Рабочие K3s/GitOps-манифесты и `docker-compose.prod.yml` этим изменением не затрагиваются. Приложение запускается из собранного Python-окружения без установки dev-зависимостей при старте. Личные уведомления и команды бота работают только в личном чате; публичная лента новых анкет настраивается отдельно.
